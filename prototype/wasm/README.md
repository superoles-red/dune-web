# PoC WASM-бэкенда (этап 2, прототип)

Рабочий прототип главной технической идеи этапа 2 из [docs/WASM-BACKEND.md](../../docs/WASM-BACKEND.md):
**генерировать WASM на устройстве чистым Python, без C-компилятора**, а рантайм держать
отдельным заранее собранным модулем.

Это не весь бэкенд и не игра, а доказательство трёх вещей:

1. бинарник WASM можно собрать вручную, без `wasm-ld`/`emcc`/`wat2wasm` (кодировщик ниже — stdlib Python);
2. транслированный код можно разложить по 4 КиБ страницам PC и раздавать через `br_table`
   (никакого интерпретатора и fetch/decode в рантайме), включая RAM-варианты
   (самомодифицирующийся код / Z80-образы) с проверкой байтов образа;
3. два модуля связываются через общую линейную память, импорты хелперов рантайма и
   `call_indirect` из рантайма в сгенерированный код — так, как это будет в продукте.

Всё остальное (реальный `runtime.wasm` на emcc 3.1.74, ROM, 40 382 обработчика, Pyodide,
OPFS-кэш, телефон) — следующие этапы, см. дизайн.

## Файлы

| Файл | Что это |
|---|---|
| `wasm_emit.py` | минимальный кодировщик WASM (binary format 1): LEB128, секции type/import/function/table/memory/export/code, i32/i64 load/store, арифметика, `block`/`loop`/`if`/`br`/`br_if`/`br_table`/`call`/`call_indirect`/`return`. Только stdlib, Python 3.9+. |
| `emit_poc.py` | «эмиттер»: синтетический набор транслированных операций (`MOVE.W D0,(A0)+`, `ADDQ.L #1,D0`, `BCC`, `BRA`, `RTS`, `STOP`, RAM-обработчик с guard’ом) → `poc.wasm`; плюс вспомогательные модули для стресс-тестов и замеров. Пишет `build/*.wasm` и `build/poc-meta.json`. |
| `run_poc.mjs` | Node 24, без npm: инстанцирует модули, подставляет JS-стабы хелперов рантайма (`read_mem`, `write_mem`, `logic_flags`, `arithmetic`, `condition`, `push32`, `pop32`, `set_sr`, `fail`) с той же семантикой, что в `runtime.h`, гоняет программу, проверяет регистры/память/переходы/счётчики циклов/пути ошибок/диспетчеризацию и печатает метрики. |
| `build/` | сгенерированные `.wasm`/`poc-meta.json`; в git не попадает (`.gitignore`). |

## Как запустить

```sh
cd dune-web

# 1. сгенерировать модули (системный python3 3.9 тоже подходит — код stdlib-совместимый)
python3 prototype/wasm/emit_poc.py
#    или: python3 prototype/wasm/emit_poc.py

# 2. проверить (Node 24)
/usr/local/bin/node prototype/wasm/run_poc.mjs
```

Успех — последняя строка `OK: N checks passed`, код выхода 0. Скрипты можно запускать из любого
каталога: `emit_poc.py` кладёт результат в `prototype/wasm/build/` рядом с собой, `run_poc.mjs`
читает оттуда же.

## Что именно проверяется (118 проверок)

- **ABI-раскладка.** `poc-meta.json` (её пишет эмиттер) сверяется с константами теста: смещения
  `CPU` (d/a/pc/sr/fault/cycles/instruction_cycles), адрес RAM-окна, порядок и сигнатуры
  импортов. Случайное изменение ABI валит тест.
- **Кодировщик.** Оба модуля проходят `WebAssembly.validate`; собственный self-test LEB128 —
  `python3 prototype/wasm/wasm_emit.py`.
- **Исполнение.** 18 шагов синтетической программы: трасса PC совпадает с ожидаемой пошагово,
  итоговые D0–D7/A0–A7, SR, PC, halted; сумма `instruction_cycles` = 152; 64-битный счётчик
  циклов; содержимое RAM (запись `MOVE.W D0,(A0)+`) и стека (RTS); ровно ожидаемое число
  вызовов каждого хелпера (read_mem=3, write_mem=1, logic_flags=5, arithmetic=6, condition=3,
  pop32=1, set_sr=1).
- **Переходы.** Цикл `BCC6` (3 итерации, `condition` через импорт), `BRA` через границу страницы
  (0x0114 → 0x1100), скипнутая инструкция (`MOVEQ #9,D4` не выполнилась), `RTS` из RAM-страницы
  (0xFF0200) по образу `4e 75` и возврат на 0x1210.
- **RAM-варианты.** Если байты RAM-образа не совпали (`4e 75` испорчен), обработчик вызывает
  `fail(FAIL_RAM_VARIANT)` и не меняет PC — как `memcmp`-проверка в C-эмиттере.
- **Пути ошибок.** Нечётный PC, PC вне 24 бит, непереведённый слот, дырка в ROM-пространстве
  (page 0x200), пустой слот RAM-страницы — каждая даёт свой код причины, PC не меняется.
- **Диспетчеризация полной ширины.** `stress_dispatch` — 2048 слотов (32 чанка × 64), 22
  «дырки»: все 2048 слотов проверены, 0 расхождений, default-путь попадает ровно 22 раза.
- **Два модуля.** `poc-runtime.wasm` владеет памятью и таблицей функций, вызывает
  `translated_step` через `call_indirect` и считает `uint64` циклы. Итоговые CPU- и RAM-байты
  побитово совпадают с прогоном, где рантаймом был JS: доказано, что направление вызова
  «рантайм → сгенерированный код» и общая память работают.
- **Стресс реального размера страницы.** `poc-heavy.wasm` — 3 страницы по 1 344 обработчика
  (максимум реальной страницы Dune): 920 351 байт, V8 принимает; первая компиляция страницы
  ~2 мс, диспетчеризация 0,1 мкс/инструкцию. Это снимает главный риск «огромная функция на
  страницу».
- **Стоимость ABI-вызова.** Замер в Node/V8: локальный вызов ~2,4–2,5 нс; вызов экспорта
  `runtime.wasm` через импорт 2,1–4,4 нс (зависит от прогрева V8); JS-стаб 3,9–4,2 нс;
  `call_indirect` 2,1–2,2 нс. Вывод: простые
  импорты хелперов дают ~2 нс накладных на вызов — на масштабе игры это доли процента, а
  таблица функций нужна только для вызова сгенерированного кода из рантайма.

## Чего PoC НЕ проверяет (честно)

- Реальный `runtime.wasm` (emcc 3.1.74, SDL2, YMFM, VDP, web-хост) и его ABI-дескриптор —
  это этап 1/2 плана; здесь хелперы реализованы на JS с семантикой C.
- Реальный ROM и все 40 382 обработчика/3 095 Z80-вариантов; здесь 11 синтетических операций.
- Время/память Pyodide при генерации WASM вместо C и работу в браузере/на телефоне.
- 68000-страницы в RAM: у USA-дампа их нет (`memcmp`-вариантов 0), механизм поддержан
  PoC-обработчиком, но реальный эмиттер для Z80 ещё не написан.
- Точность на уровне поведения игры: будет проверяться дифференциально против C-сборки
  (см. дизайн, §13).

## Метрики последнего прогона (M1 Pro, Node 24.16, V8)

```
game.wasm            19 641 B (11 обработчиков + stress 2048 слотов)
                     без stress: 2 793 B, из них 445 B — диспетчер/ABI, 213,5 B на обработчик
runtime.wasm         172 B (память + таблица + цикл run())
heavy (3 x 1344)     920 351 B, компиляция модуля 1,3–1,5 мс
                     первый вызов страницы ~2,0–2,3 мс, warm 0,08–0,12 мкс/инструкцию
```

Эти числа — входные для оценок размера `game.wasm` и времени первого прогрева в дизайне
(§6.2, §11.3): 213 B/обработчик × 40 382 ≈ 8,6 МБ верхняя оценка «как есть»; в C-сборке emcc
весь транслированный код вместе с рантаймом и данными ROM занимает 5,27 МБ, поэтому реальная
цель — 4–9 МБ.
