# Архитектура BYOP-порта Dune

## Поток

```
[ROM игрока] ──► проверка SHA-256 (JS, страница)
                     │
                     ▼
        ┌── OPFS-кэш: rom-<sha>/core.c + meta.json ──┐ (повторный запуск)
        │                                            │
        ▼                                            │
[Web Worker]                                         │
  Pyodide (CPython 3.13 → WASM)                      │
  ├─ genesis_recompiler (MIT ReArrakis): анализ 68000/Z80
  ├─ dune_build.py: паспорт дампа, Z80-образы, discovery, вызов CLI in-process
  └─ emit: [pinned runtime v2] + [ROM] + [транслированный код игры]
                     │
                     ▼
        SHA-256 сверка с эталонным ядром
                     │
                     ▼
   кэш в OPFS ←──────┘   (сейчас: C-ядро; далее: WASM-модуль игры)
```

## Компоненты

| Путь | Роль |
|---|---|
| `web/index.html`, `web/app.mjs` | оболочка: ROM, паспорт дампа, прогресс, сверка, сейвы |
| `web/recompiler.worker.js` | воркер: Pyodide, распаковка перекомпилятора, прогресс, OPFS-кэш |
| `web/py-src/driver.py` | вход в Pyodide: ROM → C, сверка SHA, JSON-результат |
| `web/py-src/dune_build.py` | порт `tools/build_dune.py`: discovery точек входа, Z80-образы, аргументы CLI |
| `tools/recompiler_overlay/` | два патча ReArrakis (MIT): `--pinned-runtime`, `--window-title` |
| `runtime/` | точная runtime-преамбула v2 (наш MIT-код + ReArrakis) и манифест SHA |
| `profiles/dune-us.json` | паспорт поддерживаемого дампа: размер, SHA-256, точки входа, таблицы |
| `tools/bundle_web.py` | сборка `web/py-package.zip`, `web/vendor/pyodide`, `web/reference.json` |
| `tools/build_runtime.py`, `tools/verify.py` | точная сборка/проверка рантайма и сверка ядра |
| `tools/serve.py` | локальный сервер с COOP/COEP |
| `web/saves/` | формат сохранений, совместимый со старой версией |

## Границы данных

- **В git:** MIT-код ReArrakis, наша адаптация, runtime-преамбула (код, без ROM), профиль
  дампа (размер/адреса), скрипты, тесты, документация.
- **Не в git:** ROM, сгенерированное ядро, извлечённые ассеты игры, кэш.
- **У игрока в браузере:** ROM, собранное ядро (OPFS), сохранения (localStorage + файлы),
  настройки. Ничего не отправляется на сервер.

## Почему runtime отдельно

Сгенерированный C = преамбула рантайма (CPU, VDP, звук, ввод, web-хост, сейвы) + массив ROM +
40 382 обработчика инструкций. Рантайм от ROM не зависит — его можно зафиксировать, проверять
по SHA и переиспользовать. Это же нужно для WASM-этапа: рантайм собирается заранее, а из ROM
генерируется только модуль с обработчиками.

## ABI сохранений

Сохранения старой версии — сериализованный `DuneSaveState` (`DSAV` v2) внутри JSON-конверта.
Новый порт обязан сохранить ту же структуру и смещения, иначе перенос сейвов невозможен.
Правила и смещения — в [SAVES.md](SAVES.md), устройство рантайма — в [RUNTIME.md](RUNTIME.md).

## Следующий шаг (этап 2)

Заменить «C → emcc» на «WASM → устройство»:

1. `runtime.wasm` собирается заранее (emcc 3.1.74, SDL2, те же экспорты `EMSCRIPTEN_KEEPALIVE`).
2. На устройстве Python-эмиттер из ROM генерирует `game.wasm`: функции-обработчики,
   диспетчеризация по PC, RAM-варианты; связывание через импорты рантайма и общую память.
3. Кэш в OPFS хранит `game.wasm` + метаданные; прогресс — по фазам.
4. Совместимость сейвов остаётся: `DuneSaveState` живёт в рантайме и не генерируется из ROM.

Дизайн и PoC — в [WASM-BACKEND.md](WASM-BACKEND.md).
